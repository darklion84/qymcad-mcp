# ADR 0062: Trim

- Status: accepted (2026-11-16).
- Related: ADR 0059 (sheet bodies), 0061 (Replace face and Stitch), 0041 (re-pick), 0056/0057 (one tool = one app action); `tasks/surfaces-research.md` sections 1, 6, 10. Package T, step T3.

## What the tool is

`trim` is the app's `Trim { src, tool, keep, body }`: the sheet `src` is cut by the body `tool` (a solid or a sheet) and the connected piece of the sheet nearest to the point `keep` stays. The node's body is a NEW sheet (the node id is its id); `src` is consumed, `tool` is not and goes on cutting. The result carries no numbers: the piece is chosen by a point, not by an index, so it survives an edit of the base (a point answers "which piece is nearest to this place" the same way after a shift or a stretch; tested with depth 40 to 60: 1200 to 1800).

The kernel's refusals come back natively and the edit is rolled back, document untouched: a tool that does not divide the sheet ("operation failed: Trim"), a tool that misses, the plate a sheet was copied from used as its own tool (the sheet lies on the plate's face). Nothing is invented on top of them.

## The frame of `keep` (FIRST question of the step, decided from the app's code)

The research guessed that the GUI stores `keep` in world coordinates and the kernel reads it part-locally, so that a Trim on a placed Part would keep the wrong piece (an app defect). Reading the code says otherwise for the GUI flow:

- The core does not convert `keep`: `prep_trim` (qymcad-core `model/regen/prep_ops.rs`) passes it to `k.trim(body, src, tool, keep)` and the kernel's `Shape::trim(tool, keep)` works part-local.
- The GUI stores `ray_at` from `pick_face_ray` (`qymcad-pick/src/body_hits.rs`): the mesh vertices transformed by `body_display_transform(body, ctx)` = `relative_transform(owner, active context)` (`model/components.rs`; base == component gives the identity).
- The Part tools (`PartCtx`, `start_trim_cmd`) exist only inside a Part (`ctx_holds_bodies` is true for a Part only), so the active context IS the owner and the display frame is the Part's own frame: part-local.

So there is no defect and no FINDINGS entry. The server takes `keep` part-local, like topology and `select` coordinates (the server instructions, "Geometry frames"), and the tool text says so. Tested on a Part placed with an offset and a quarter turn: the same local point keeps the same piece as on an unplaced Part, and the point's WORLD image, read part-locally, keeps the other one. Not probed: a Trim whose sheet and tool lie in Parts that are placed differently (see below).

## Decisions

- Input kinds are the GUI's (`msg-trim-pick-sheet`, `msg-trim-pick-tool`): `body` must be a sheet (a solid is refused with the same words as ADR 0061: "is a solid; the body to trim must be a sheet"), `tool` any live body that is not the sheet itself. A consumed body, a mesh body, an unknown id and a non-finite `keep` are refused before a node is laid. `body` and `tool` and `keep` are required (a sheet is never a default body, ADR 0059).
- Tool and sheet must be in the SAME Part. The kernel works in one part-local frame; a tool from another Part would be read in the wrong frame. The GUI offers Part tools inside one Part only and `body_boolean` already refuses "same part"; the server refuses the same way. This is a design choice of the server, not a measured limit of the app: the different-Part case was not probed in the app.
- The node is wrapped in `in_component(body_owner(src))`, so it lands in the sheet's Part and not in the active one (tested with another Part active).
- `feature` re-picks as the app's edit mode does (`update.rs`): `body`, `tool` and/or `keep` are replaced TOGETHER as one write (the node holds `src`, `tool` and `keep` and the re-pick rewrites them in one step). A new `body` needs its own `keep` (the old point lies on the old sheet), otherwise it is refused. A sheet this node consumes is free again; a tool or a sheet built after the node, a solid, a body consumed by another node, a tool equal to the sheet and a node of another kind are refused; a re-pick whose rebuild fails (a tool that misses) is rolled back and leaves the document as it was. `name` is refused with `feature`.
- `sheet_input` of ADR 0061 was split into `live_input` (live, not a mesh) and `built_before` so that a tool, which may be a solid, shares the checks without the "must be a sheet" one; the sheet checks of `surface_replace` and `stitch` are unchanged (T2 tests re-run green).

## What cannot be shown through the server

The app keeps the unchanged sheet when a Trim cuts nothing on a REBUILD (core `run.rs`): the node stays green. The server rolls back every edit that makes a node fail (`atomic`), and a Trim that cuts nothing is refused at creation, so a red or "kept" Trim node cannot be reached from the tool. The parameter edit that makes the tool miss is tested as a refusal with the document unchanged. A file written by the GUI that holds such a node is opened as the app opens it (not probed).

## Tests

Engine `trim.rs` (numbers of the app's `trim.rs`: left 30 x 40 = 1200 with the sheet consumed and the tool not, right 1200 with the centroid beyond the cut, a tool that misses, a sheet as the tool, follows the base 1800, a placed Part with the local and the world point, the node's Part, refusals, re-pick of point, tool and sheet, a re-pick that misses, save/open and the app's own edit path `gui_edit_param_model`), MCP `t3_trim.rs` (results, refusals, missing arguments, `feature`, batch with rollback, undo, save/open).
